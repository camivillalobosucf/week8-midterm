## 1. Firestore Data Structure

The top-level collection is `users`, with each document keyed by Firebase `uid`. Under each user, a subcollection `entries` holds all baby activity logs.

```
firestore/
└── users/
    └── {uid}/                          ← one doc per authenticated user
        ├── displayName: "Jane"         ← optional profile fields
        ├── createdAt: Timestamp
        └── entries/                    ← subcollection
            └── {entryId}/
                ├── type: "feeding" | "diaper" | "sleep"
                ├── timestamp: Timestamp   ← when the activity happened
                ├── createdAt: Timestamp   ← when the log was created
                ├── notes: string          ← optional free text
                │
                │  ── feeding-specific ──
                ├── feedingType: "breast" | "bottle" | "solid"
                ├── amount: number         ← ml or oz (bottle/solid)
                ├── duration: number       ← minutes (breastfeeding)
                │
                │  ── diaper-specific ──
                ├── diaperType: "wet" | "dirty" | "both" | "dry"
                │
                │  ── sleep-specific ──
                ├── sleepStart: Timestamp
                └── sleepEnd: Timestamp    ← null if still sleeping
```

**Key decisions:**
- Flat subcollection (not nested maps) so you can query, filter, and paginate efficiently.
- All entries in one `entries` subcollection, discriminated by `type`. Avoids three separate subcollections that can't be queried together.
- `timestamp` = the real-world event time; `createdAt` = the Firestore write time. This lets users backfill entries.
- Security rules scope every read/write to `request.auth.uid == userId`.

## 3. Key Components

| Component | Responsibility |
|---|---|
| `AuthContext` | Listens to `onAuthStateChanged`, exposes `currentUser` and loading state app-wide |
| `ProtectedRoute` | Wraps all logged-in routes; redirects unauthenticated users to `/login` |
| `Navbar` | Navigation links + logout button; only renders on protected pages |
| `Dashboard` | Queries today's entries, shows counts and totals per type |
| `SummaryCard` | Visual card for one activity type (icon, count, totals) |
| `EntryList` + `EntryItem` | Paginated/filtered list with inline edit/delete per row |
| `EntryForm` | Shared add/edit form — receives `initialData` prop; empty = add mode |
| `FeedingFields / DiaperFields / SleepFields` | Conditionally rendered inside `EntryForm` based on selected type |
| `entriesService.js` | Firestore CRUD abstracted from UI — components never call Firestore directly |
| `useEntries.js` | Custom hook that calls `entriesService`, manages local state + loading/error |

## Key Architectural Rules to Keep in Mind

- **Never call Firestore directly from a component.** All Firestore calls go through `entriesService.js`. Components call the service via `useEntries.js`.
- **`currentUser.uid` is always the Firestore path prefix.** The path `users/{uid}/entries/{entryId}` enforces data isolation at the database level, not just the UI.
- **Use `onSnapshot` on the entries list** so edits and deletes update instantly without a manual refresh.
- **`timestamp` on entries should be user-selected**, not auto-set, so parents can log events retroactively.

## Firestore Security Rules

Go to **Firebase Console → Firestore Database → Rules** and replace everything with:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{userId}/entries/{entryId} {
      allow read, write: if request.auth != null && request.auth.uid == userId;
    }
  }
}
```

Click **Publish**. This rule means:
- A logged-in user can only read/write entries where the `{userId}` segment in the path matches their own Firebase `uid`
- Any unauthenticated request or cross-user access is rejected at the database level
